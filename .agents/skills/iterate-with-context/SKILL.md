# Iterate with context

Start from the user's objective, constraints and raw evidence. Distinguish observed facts, assumptions and proposals.

- Produce a concrete first pass rather than a broad questionnaire. Ask only for missing information that changes the decision; continue independent useful work.
- Identify the strongest trade-off or failure mode. Challenge weak assumptions without substituting your own product vision for the user's.
- Keep iterations short. Incorporate corrections, preserve accepted decisions and make the next unresolved choice explicit.
- Prefer a small coherent outcome over a growing feature inventory. Explain what is built, deferred or merely a concept.
- Persist accepted rationale in the requested project document when authorised; do not turn brainstorming into implementation or external messages automatically.
- Use sources for claims that need current or specialist evidence. Label inference and uncertainty.

Once implementation is requested, use [demo-not-doc](../demo-not-doc/SKILL.md) for a product experiment or [bau-workflow](../bau-workflow/SKILL.md) for a focused maintenance change. Do not keep writing proposals when the user has asked to build.
